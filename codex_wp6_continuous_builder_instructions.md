# WP6 Codex Instructions — Continuous Builder / Backward Ratio-Adjusted Series v1

Status: **ready for Codex implementation**  
Target branch: `wp6-continuous-builder`  
Depends on: WP3 data schema, WP4 raw ingest/normalization, WP5 roll engine  
Primary output: `continuous_daily`  
Non-goal: CPD/features/model training/broker execution

## 0. Goal

Implement the v1 continuous series builder that converts:

```text
contract_master + contracts_daily + lead_map + roll_events
```

into:

```text
continuous_daily
```

The output series is the **canonical signal-generation price series** for WP7+ feature engineering and CPD-LSTM research.

The implementation must be deterministic, lineage-aware, no-lookahead-safe, and testable offline with synthetic data.

The v1 continuous series is:

```text
series_id       = v1_back_ratio_settle
builder_version = continuous_builder_v1
method          = backward ratio-adjusted settlement series
roll source     = lead_map + roll_events generated by WP5
price source    = contracts_daily.settle_price selected by WP4
```

## 1. Scope

### In scope

1. Add a continuous builder module.
2. Build `continuous_daily` rows for selected roots/date ranges.
3. Compute cumulative backward ratio adjustment factors.
4. Compute adjusted settlement price and daily return.
5. Emit rows even when a price is unusable, with `is_usable_for_signal=false` and quality flags.
6. Validate continuous series with a QA report.
7. Add CLI commands for build and QA.
8. Add offline smoke command and unit tests using synthetic fixtures.
9. Update docs and Makefile.
10. Preserve WP3 schema compatibility.

### Explicitly out of scope

Do **not** implement these in WP6:

- CPD computation.
- `features_daily`.
- TSMOM.
- CPD-LSTM.
- walk-forward evaluation.
- IBKR/paper/live execution.
- Databento vendor calls.
- broker-facing contract resolution.
- vendor continuous symbols as a signal source.

## 2. Key design rule

`continuous_daily` is **research/signal-only**.

It must never be used as a broker contract identifier.

Broker-facing paths must use:

```text
lead_map.lead_raw_symbol
targets_daily.lead_raw_symbol
order_intents.raw_symbol
```

not `series_id`, Databento continuous symbols, or adjusted prices.

## 3. Important background

Databento supports multiple symbology types including `raw_symbol`, `instrument_id`, `parent`, and `continuous`. Its continuous contract symbology maps to an actual tradable instrument on a given date, but the continuous prices are original/unadjusted prices, not retail-style back-adjusted prices.

This project therefore builds its own signal series from:

- actual contract rows in `contracts_daily`;
- the WP5 `lead_map`;
- WP5 `roll_events`.

Do not pull or trust vendor continuous series for WP6.

## 4. Data schema contract

```text
series_id                 TEXT
```

Primary key:

```text

```

Recommended physical path:

```text

```

If the current repo already has storage helpers from WP4, reuse them. Otherwise keep storage minimal and isolated.

### 5.3 `roll_events`

```text
roll_event_id

```

`ratio_adjustment` should be:

```text
to_settle / from_settle
```

using the roll reference date, normally `trigger_date`.

WP6 may recompute the ratio from `from_settle` and `to_settle` if `ratio_adjustment` is null but both prices are positive.

If the ratio cannot be determined and the roll event falls inside the build date range, fail in strict mode.

## 6. Series construction

### 6.1 Selected raw price

For each row in `lead_map`:

```text
as_of_date = d
root = r
lead_raw_symbol = c
```

join:

```text
contracts_daily.trade_date = d
contracts_daily.root = r
contracts_daily.raw_symbol = c
```

Set:

```text
raw_settle_price = contracts_daily.settle_price
settle_status    = contracts_daily.settle_status
```

If the matching row is missing or `settle_price` is missing/nonpositive:

```text
adj_settle_price     = null
daily_return         = null
is_usable_for_signal = false
quality_flags        includes missing_raw_price or nonpositive_raw_price
```

Do not silently fill with another contract.

### 6.2 Backward ratio adjustment

For each root independently, sort rows by `as_of_date`.

For each roll event with `effective_date = e` and ratio `q`:

```text
q = to_settle / from_settle
```

The cumulative adjustment factor for dates **strictly before** `e` must include `q`; dates `e` and later must not include that event's `q`.

For a date `d`:

```text
adj_factor(d) = product(q_k for roll events k where effective_date_k > d)
adj_settle_price(d) = raw_settle_price(d) * adj_factor(d)
```

Reverse traversal implementation:

```python
factor = 1.0
for d in reversed(root_dates):
    adj_factor[d] = factor
    if there is a roll event with effective_date == d:
        factor *= ratio_adjustment_for_that_event
```

This deliberately means:

- the new contract on the roll effective date is left at the current scale;
- all prior history is restated by the roll ratio;
- old contract price on the roll reference date aligns to the new contract scale;
- returns before a future roll are not changed except by a constant scale factor;
- return-based features remain stable under future restatement.

### 6.3 Daily return

For each root and series:

```text
daily_return(d) = adj_settle_price(d) / adj_settle_price(prev_usable_or_prev_calendar_row) - 1
```

v1 should use the **previous chronological row** for that root, not the previous usable row, to avoid hiding gaps.

If either current or previous adjusted price is missing/nonpositive:

```text
daily_return = null
is_usable_for_signal = false
quality_flags includes missing_return_input
```

The first row per root has:

```text
daily_return = null
quality_flags includes warmup_first_row
```

### 6.4 Roll date behavior

On a roll effective date:

```text
continuous_daily.roll_flag = true
continuous_daily.roll_event_id = event id
lead_raw_symbol = to_raw_symbol
```

The return from the previous date into the roll effective date should primarily reflect the **new contract's price movement after the roll reference date**, not the raw spread between old and new contracts.

This should be enforced in tests.

## 7. No-lookahead requirements

The builder must satisfy these conditions:

1. It must not use vendor continuous prices.
2. It must not use future volume to decide the lead contract. WP5 already handles this; WP6 must consume only `lead_map`.
3. If building with `end_date < roll_event.effective_date`, that future roll must not alter prior `adj_factor`.
4. If building a historical full sample, later roll events may restate earlier price levels by a constant factor, but return-based features should remain invariant. This is accepted for research series.
5. Every output row must carry `snapshot_id` and `builder_version`.

Add tests for point 3.

## 8. Strictness policy

Add a config object or mapping with at least:

```yaml
continuous:
  series_id: v1_back_ratio_settle
  builder_version: continuous_builder_v1
  strict_roll_ratio: true
  allow_close_fallback: true
  allowed_settle_statuses:
    - final
    - preliminary
    - close_fallback
  blocked_settle_statuses:
    - missing
  max_abs_daily_return_warning: 0.20
  max_abs_daily_return_error: 0.50
```

Behavior:

- `strict_roll_ratio=true`: missing/nonpositive roll ratio is fatal.
- `allow_close_fallback=true`: close fallback is usable but tagged.
- `settle_status=missing`: unusable row.
- very large daily returns should be warnings/errors according to thresholds, unless they can be explained by a known data issue.

## 9. QA report

Create something analogous to WP5's QA pattern:

```python
@dataclass(frozen=True)
class ContinuousQaIssue:
    code: str
    severity: str  # "error" or "warning"
    message: str
    details: dict[str, object] = field(default_factory=dict)

@dataclass(frozen=True)
class ContinuousQaReport:
    snapshot_id: str
    series_id: str
    builder_version: str
    summary: dict[str, object]
    issues: tuple[ContinuousQaIssue, ...] = ()
```

Methods:

```python
has_errors
has_warnings
to_dict()
to_markdown()
```

QA should check at least:

### Fatal errors

- duplicate primary keys: `(series_id, as_of_date, root)`;
- missing required columns;
- `adj_factor` null, nonpositive, infinite, or NaN;
- `adj_settle_price` nonpositive when `is_usable_for_signal=true`;
- `lead_raw_symbol` missing from `lead_map`;
- roll event with missing/nonpositive ratio in strict mode;
- multiple roll events for same `(root, effective_date)`;
- output coverage missing a `lead_map` row without a documented quality reason.

### Warnings

- `settle_status=close_fallback`;
- missing raw price;
- missing return input;
- `abs(daily_return)` above warning threshold;
- large roll basis;
- root has too few usable rows;
- root coverage starts after requested start or ends before requested end.

### Summary fields

Include at least:

```text
row_count
root_coverage
date_coverage
usable_fraction_by_root
roll_count_by_root
close_fallback_count
missing_price_count
missing_return_count
large_return_count
fatal_error_count
warning_count
```

Write QA artifacts to:

```text
artifacts/wp6/continuous_qa_<snapshot_id>_<series_id>.json
artifacts/wp6/continuous_qa_<snapshot_id>_<series_id>.md
```

## 13. Required unit tests

Use synthetic data only. Do not call Databento or IBKR.

### 13.1 No-roll series

Input:

- one root;
- one contract;
- five dates;
- lead never changes.

Expected:

- `adj_factor=1.0` for all rows;
- `adj_settle_price=raw_settle_price`;
- first `daily_return=null`;
- subsequent returns match raw price returns.

### 13.2 Single volume roll

Synthetic prices:

```text
D1 old=100
D2 old=101
D3 old=102, new=204  # trigger/reference date, ratio=2.0
D4 new=206           # effective date
D5 new=208
```

Expected:

```text
factor D1,D2,D3 = 2.0
factor D4,D5    = 1.0
adj D3          = 204
adj D4          = 206
return D4       = 206/204 - 1
```

This is the most important test.

### 13.3 Future roll must not affect truncated build

Build only through D2 while roll effective date is D4.

Expected:

```text
factor D1,D2 = 1.0
```

This catches accidental application of future roll events outside the build window.

### 13.4 Multiple rolls

Two roll events with ratios `2.0` and `0.5`.

Expected:

```text
dates before first roll have factor 1.0 if product is 2.0*0.5=1.0
dates between rolls have factor 0.5
dates after second roll have factor 1.0
```

Use a clear synthetic example and assert exact factors.

### 13.5 Missing raw price

Lead map row exists but `contracts_daily` lacks the matching lead contract price.

Expected:

- output row still exists;
- `raw_settle_price=null`;
- `adj_settle_price=null`;
- `daily_return=null`;
- `is_usable_for_signal=false`;
- quality flags include `missing_raw_price`.

### 13.6 Missing roll ratio in strict mode

Roll event inside range has null ratio and insufficient `from_settle/to_settle`.

Expected:

- build raises `ContinuousBuildError`, or QA has fatal error depending on implementation style;
- it must not silently use ratio `1.0`.

### 13.7 Close fallback tagging

`settle_status=close_fallback` with positive price.

Expected:

- usable if config allows close fallback;
- quality flags include `close_fallback`.

### 13.8 Duplicate output key QA

Create duplicate continuous rows.

Expected:

- QA fatal `duplicate_primary_keys`.

### 13.9 Large return warning/error

Create a synthetic adjusted return above warning threshold.

Expected:

- QA warning if above `max_abs_daily_return_warning`;
- QA error if above `max_abs_daily_return_error`.

### 13.10 Roll effective row links event id

On effective date:

- `roll_flag=true`;
- `roll_event_id` matches the roll event;
- other dates are false/null.

## 16. Implementation notes

- Use `pandas` and `pyarrow` only if already available from project dependencies.
- Keep time/date columns as `datetime.date` in core logic and convert only at I/O boundaries.
- Do not introduce a database dependency unless already used by the repo.
- Prefer pure functions for core logic; CLI should be a thin wrapper.
- Do not mutate input DataFrames in-place.
- Sort deterministically by `root`, `as_of_date`, `lead_raw_symbol`.
- Use stable ids/hashes from existing `cpdshadow.ids` if helpful.
- Preserve existing public APIs and tests.
